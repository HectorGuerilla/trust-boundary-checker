# Trust-Boundary Audit Template

Use this before launching a README, landing page, docs homepage, CLI, SDK, API, or AI tool.

## 1. Promise

Current one-sentence promise:

> 

Can a stranger answer in 10 seconds: who is it for, what painful job does it do, what output do they get, and what does it replace?

Rewrite pattern:

> [Tool] helps [specific user] [achieve measurable result] without [specific friction/risk].

## 2. Trust boundary

| Question | Answer | Visible before install? | Fix |
|---|---|---:|---|
| What runs locally vs remotely? | | Yes/No | |
| What data leaves the machine/account? | | Yes/No | |
| What tokens/permissions/scopes are needed? | | Yes/No | |
| What is stored, logged, retained, or deleted? | | Yes/No | |
| What write actions can happen? | | Yes/No | |
| How do users revoke/uninstall? | | Yes/No | |

## 3. First-run path

1. Arrives from: ____
2. Understands promise after: ____ seconds
3. Installs/opens with: ____
4. Provides: ____
5. Runs/clicks: ____
6. Sees useful output: ____
7. Knows it worked because: ____

## 4. Proof

Add at least one near the install button: screenshot, terminal output, tiny example, before/after, benchmark, limitation, failure case, source link, changelog.

## 5. Objections

- Why should I trust this?
- Why not do this manually?
- Will it work with my stack?
- What does it cost: money, time, risk?
- What if I want to leave?

## 6. Top fixes

- [ ] Replace vague tagline with user + job + outcome.
- [ ] Add trust-boundary note: data, permissions, storage, deletion.
- [ ] Add quickstart with expected output.
- [ ] Add limits and failure modes.
- [ ] Add clear next action.
